# HIRI UI/UX DESIGN SYSTEM V2

## Professional Product Design + Experimental Digital Art Direction + Cinematic Product Storytelling

---

# 1. Purpose

This document is the authoritative visual, interaction, motion, 3D, frontend-composition, and product-writing specification for HIRI.

All HIRI frontend work must follow this document.

HIRI must not look like:

* a generic AI SaaS template
* a standard shadcn dashboard
* a conventional corporate website
* a Dribbble concept with weak usability
* a purple-gradient AI startup
* a collection of unrelated visual experiments

HIRI must develop a recognizable digital identity.

The objective is:

> **Professional software that feels like it comes from the future without sacrificing trust, clarity, control, or usability.**

HIRI should make a first-time visitor think:

> “What is this?”

and then immediately understand:

> “This is a platform for operating an AI workforce.”

---

# 2. HIRI Design North Star

HIRI combines three qualities:

## Professional Product Design

The product must remain:

* usable
* structured
* trustworthy
* accessible
* responsive
* information-dense where appropriate
* suitable for real business operations

## Experimental Digital Art Direction

HIRI may use:

* creative layouts
* unusual composition
* controlled gradients
* illumination
* depth
* 2.5D
* real-time 3D
* spatial interfaces
* custom illustrations
* visual storytelling
* asymmetry
* layered scenes

when these reinforce HIRI's identity.

## Cinematic Product Storytelling

The public experience should not merely describe HIRI.

It should visually demonstrate HIRI operating.

A visitor should be able to see:

Work entering the company
→ being assigned
→ being executed
→ reaching an approval checkpoint
→ producing a business result.

# 3. Three-Layer Design Architecture

HIRI has three connected but distinct design layers.

---

## Layer A — HIRI Brand Experience

Used primarily for:

* public website
* homepage
* product storytelling
* onboarding
* launch experiences
* demonstrations
* selected empty states
* selected workforce visualizations

This layer can be:

* cinematic
* visually ambitious
* spatial
* animated
* editorial
* immersive
* more experimental

Its purpose is to create recognition and explain the HIRI concept.

---

## Layer B — HIRI Product Interface

Used primarily for:

* Dashboard
* Sales Inbox
* Workforce
* WorkItems
* Approvals
* Analytics
* settings
* integrations
* forms
* operational views
* administration

This layer must be:

* calmer
* faster
* flatter
* denser
* more predictable
* optimized for daily work

The authenticated HIRI application must not look like a 3D videogame interface.

---

## Layer C — HIRI Shared Visual Language

Both layers share:

* typography
* color logic
* geometry
* icon language
* status system
* lighting meaning
* motion principles
* AIEmployee representation
* Department representation
* WorkItem representation
* approval representation
* interaction quality

This creates one coherent HIRI identity.

# 4. Core Design Philosophy

Use this principle throughout HIRI:

# Flat when reading.

# Spatial when understanding.

# Motion when something changes.

### Flat when reading

Use normal professional interfaces for:

* forms
* tables
* conversations
* approvals
* settings
* configuration
* text-heavy screens
* detailed operational information

### Spatial when understanding

Use spatial or 3D representation for:

* AI workforce structure
* Department organization
* AIEmployee relationships
* WorkItem movement
* capability relationships
* integrations
* cross-system execution
* HIRI architecture storytelling

### Motion when something changes

Motion should communicate:

* activation
* execution
* assignment
* progress
* approval
* handoff
* completion
* error
* connection
* state change

Motion should not exist merely because animation is possible.

Therefore, Sales can be shown as active and detailed.

Future Departments such as:

* Marketing
* Customer Support

# 20. Typography Direction

Typography is one of HIRI's primary identity tools.

The system should feel:

* contemporary
* technical
* editorial
* precise
* premium

Avoid:

* default template typography
* excessive bold weights
* ten font sizes
* giant headings everywhere
* novelty futuristic fonts for body copy

Use a highly readable primary interface typeface.

A secondary display treatment may be used selectively for major public statements if it remains professional.

---

# 21. Public Typography

Public marketing pages may use larger typography than the application.

Typical desktop range:

* Hero: 56–80px depending on composition
* Major section statement: 40–64px
* Section heading: 28–40px
* Body: 16–20px
* Technical annotation: 11–13px

These are guidelines, not mandatory constants.

Typography must respond to content and viewport.

---

# 22. Product Typography

Authenticated application typography should be considerably denser.

Typical direction:

* Page title: 20–28px
* Section title: 14–18px
* Body: 13–15px
* Table content: 12–14px
* Metadata: 11–13px

The operating application must prioritize information and scanning speed.

---

# 27. Semantic Color Meaning

Colors should have stable meaning.

### Cyan / Blue

HIRI system activity

Examples:

* active system
* AI execution
* connection
* selected technical object

### Violet

Secondary workforce distinction or secondary system context.

Use sparingly.

### Amber / Gold

Human control boundary.

Examples:

* approval required
* warning
* review checkpoint

### Green

Successful business result.

Examples:

* completed
* delivered
* healthy connection

### Red

Error or destructive state.

Do not use as decoration.

# 28. Gradient Rule

Gradients are allowed.

They must be controlled.

Good uses:

* lighting
* depth
* active state
* key headline accent
* spatial atmosphere
* 3D materials
* subtle background transitions

Bad uses:

* every button
* every heading
* every card
* giant generic purple-blue hero background
* arbitrary rainbow effects

HIRI gradients must feel part of one visual system.

---

# 29. Illumination Rule

One of HIRI's signature principles:

# Light means activity.

Glow is allowed when it communicates something.

Examples:

### AIEmployee active

Controlled illumination.

### WorkItem executing

Active path illuminates.

### Tool being used

Connection temporarily lights.

### Approval required

Amber checkpoint becomes active.

### Result completed

Brief restrained green confirmation.

An idle element should not constantly glow merely because it looks attractive.

---

# 31. Corner Radius

Public visual objects may occasionally use stronger geometry.

Operational interface should remain restrained.

Recommended application values:

* controls: 4–6px
* buttons: 5–8px
* menus: 6–8px
* panels: 6–10px
* dialogs: 8–12px

Do not automatically use 20–32px rounded containers.

---

* restrained contrast

Avoid:

* heavy white borders

# 42. Product Motion

Authenticated application motion should be much quieter.

Use for:

* navigation transition
* drawers
* popovers
* status changes
* row insertion
* command palette
* loading
* progress
* approval completion

# 43. Reduced Motion

Always respect:

`prefers-reduced-motion`.

HIRI must remain understandable without animation.

For reduced motion:

* disable camera journeys
* remove continuous pulse
* stop path travel animation
* replace animated transitions with static state changes

Do not hide functionality.

# 65. Responsive Design

* desktop
* laptop
* tablet

---

# 66. Mobile 3D

On mobile:

* simplify scene
* reduce geometry
* reduce effects
* reduce animation
* avoid excessive GPU load
* preserve message

Use static or lightweight fallback if needed.

The mobile experience should still feel intentional.

---

# 67. Accessibility

Creative design does not override accessibility.

Maintain:

* semantic HTML
* keyboard navigation
* visible focus
* sufficient contrast
* ARIA where required
* correct heading structure
* readable labels
* reduced motion
* alternative information for visual scenes

3D content must never be the only method for accessing essential information.

---

# 68. Localization

HIRI supports:

* English
* French
* Arabic

All public and authenticated components must account for:

* longer French strings
* RTL Arabic
* bidi-safe business data
* responsive text
* translated status labels where defined

Do not design around English-only string lengths.

---

# 69. RTL

Arabic must correctly set:

```html
lang="ar"
dir="rtl"
```

Use logical CSS properties where appropriate.

Do not mirror:

* HIRI logo
* data semantics
* workflow meaning
* diagrams where reversing direction changes the actual process

Layout direction and process semantics are not the same thing.

---

# 70. Performance

Visual ambition must not make HIRI slow.

For large visual experiences:

* lazy-load
* code split
* optimize geometry
* optimize textures
* compress assets
* limit effects
* reduce shader complexity
* avoid continuous expensive renders

Do not block initial page functionality on heavy 3D.

---

# 71. 3D Loading Strategy

If real 3D is introduced:

Initial page should load:

1. structure
2. typography
3. primary actions

Then progressively load:

4. 3D environment
5. richer assets

Provide a visually acceptable fallback.

---

# 72. No GPU Infrastructure Requirement

HIRI's visual frontend must not require HIRI server-side GPU infrastructure.

Client-side WebGL may be used when appropriate.

GPU infrastructure is not an MVP backend requirement.

---

# 73. Dependency Rule

Before adding:

* Three.js
* React Three Fiber
* Drei
* GSAP
* Motion
* Lenis
* Spline runtime
* another animation framework

verify:

1. existing dependency cannot solve it
2. package is maintained
3. license is acceptable
4. bundle impact is reasonable
5. benefit is meaningful
6. accessibility remains possible
7. performance fallback exists

Do not install visual dependencies impulsively.

---

# 74. Motion Libraries

Prefer one coherent motion strategy.

Do not combine several animation libraries without a strong reason.

Use CSS for simple interactions.

Use a dedicated motion library for complex state animation when justified.

Use WebGL animation only for true spatial experiences.

* generic AI brain
* random particle field
* random futuristic cube
* robot mascots
* enormous pill buttons
* excessive glassmorphism
* purple gradient everywhere

These patterns may only appear if there is a deliberate HIRI-specific reason.

# 78. Existing UI Modification Rule

4. inspect adjacent components

Preserve working behavior.

## HIRI App

# 84. Visual Development Workflow

Do not redesign the entire frontend in one uncontrolled pass.

For significant design changes:

```text
Define direction
→ implement one representative area
→ run application
→ visually inspect
→ approve or revise
→ establish reusable patterns
→ expand carefully
```

Visual acceptance matters.

Passing tests does not prove good design.

# 85. Screenshot Review Rule

For major UI work, inspect the actual rendered result.

Do not approve a redesign only from:

* file list
* test results
* Codex description
* CSS diff

The interface must be visually reviewed.

# 89. Final Design Rule

Do not ask:

> How can we make this look more futuristic?

Ask:

> How would HIRI visualize this concept?

Do not ask:

> What animation can we add?

Ask:

> What is changing in the system, and should the user see that change?

Do not ask:

> What 3D object would look cool here?

Ask:

> What HIRI structure or business process would become easier to understand spatially?

HIRI should combine:

**Professional software engineering

* distinctive digital art direction
* product-specific spatial visualization
* disciplined interaction design
* cinematic storytelling where appropriate.**

The public experience should create curiosity.

The product interface should create confidence.

The visual language should make HIRI recognizable.

The final objective is not:

> “a beautiful AI SaaS website.”

The objective is:

# A digital world and operating interface that could only belong to HIRI.
